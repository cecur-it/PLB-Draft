# Telemetry Documentation Assessment

## Scope and method

Assessed `PLB_Telemetry_Onboarding_Plan.md` (the **Plan**) and `PLB_Playbook_Draft.md` (the **Playbook**) against `PLB_Assets.csv`, repository source, upstream Fluent Bit source, and vendor documentation. No production service, network appliance, credential, or site endpoint was accessed.

Confidence meanings:

- **execution**: the cited command was run locally and its observed result is reported. Container and mocked-test execution is not evidence from production appliances or a live CS3 stack.
- **code reading**: the claim was traced to the cited implementation, but the runtime path was not exercised. Deployment configuration and runtime preconditions remain assumptions.
- **inference**: the conclusion rests on documentation, naming, structure, or upstream vendor material without confirming the exact target. The recommended fix states the check needed to upgrade it.
- **unverifiable** is a verdict, not a confidence level: the available artifacts cannot establish correctness on the target system.

### Corrected relay validation

A replacement **example**, not a shipped repository fragment, was also executed with synthetic RFC3164 messages on Fluent Bit 5.1.5. It used `Name syslog`, `Mode udp|tcp`, `Parser syslog-rfc3164`, `Source_Address_Key source_ip`, regex sender conditions, the repository Lua normalizer, and no `Raw_Message_Key`.

Observed after dry-run and loopback UDP/TCP input:

```text
configuration test is successful
"agentName":"TEST-DEVICE"
"fields":{...,"source_ip":"udp://127.0.0.1:58666"}
"message":"udp password=[REDACTED]"
"fields":{...,"source_ip":"tcp://127.0.0.1:45844"}
"message":"tcp Bearer [REDACTED]"
```

The generalized parser/relay fragment was subsequently extracted directly from `General_Playbook.md` and rerun from its validation directory with `docker run --rm --network none -v "$PWD:/lab:ro" fluent/fluent-bit:5.1.5-debug /lab/smoke.sh`. It printed `configuration test is successful`, mapped UDP/TCP `agentName:"TEST-DEVICE"` records, redacted both test secrets, and `DOCUMENTED_RELAY_SMOKE_PASS`.

This proves only the synthetic local configuration. The sender value includes transport and source port, so exact-IP equality is wrong; production mappings must account for observed NAT/transport/port form. Parser acceptance and message identity for every real device format remain lab gates.

## Overall verdict

**The documents are strong worked templates but are not sufficient as-is to produce production-ready generalized onboarding and installation documents.** Most API, durability, inventory, and native-feature limitations are unusually well documented. However, the central raw-relay attribution design is disproven by execution, and several installation/API references need correction. The generalized documents can proceed only by replacing that design, carrying forward code-backed behavior, and preserving target-device/live-stack gates.

### Blocking gaps

1. **Relay attribution:** raw UDP/TCP `Source_Address_Key` does not populate sender fields in `Format none`; exact-IP mappings therefore collapse to relay identity.
2. **Exact device validation:** Cisco custom-port CLI, FortiGate message identity, Meraki MS source behavior, real parser acceptance, and Dashboard/internet-outage behavior remain unexecuted.
3. **Inventory reconciliation:** duplicate firewall addressing and the 4948E OS naming conflict require owner/device evidence.
4. **Installation correctness:** dry-run mutation, the Ollama unit name, model initialization, environment loading, Compose context, the site-specific Compose inventory mount, and rollback boundaries must be corrected.
5. **Durable production acceptance:** no live CS3/OpenSearch installation, fresh post-restart ingest, fleet recovery, outage, capacity, or restore test was performed.
6. **Production control limitations:** runtime fleet/IAM persistence needs remediation or explicit pilot risk acceptance; stale Errow routes and bounded audit export must not be carried into operational guidance.
